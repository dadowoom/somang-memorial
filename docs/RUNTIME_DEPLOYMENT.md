# 소망 실행 계정과 배포 유지 절차

2026-09-08 적용 기록과 이후 배포 절차입니다. 소망 앱은 `somangapp`
UID/GID **998**로 전환했고, 기존 `dist` 44개 파일의 내용과 배포 Git SHA는
그대로 유지했습니다. 외부 백업 암호화 전환과 다운로드 복구 검사도
01:28 KST에 완료했습니다. 실행·권한 준비 도구의 서버 설치와 기존 배포
스크립트 연결, 현재 릴리스의 권한 점검도 완료했습니다. 아래 릴리스 보관
도구의 설치·적용은 별도 검토 후 진행하며, 이 문서 추가 자체가 보관 실행을
의미하지는 않습니다.

## 목적과 고정 범위

소망 앱이 침해되더라도 서버 전체 관리자 권한을 갖지 않도록 앱을
`somangapp`으로 실행합니다. 여러 서비스를 관리하는 기존 root PM2는
유지하고 **소망 프로세스만** 바꿉니다.

| 항목 | 고정값 |
|---|---|
| PM2 앱 이름 | `somang-memorial` |
| 앱 계정·기본 그룹 | `somangapp`·`somangapp` |
| 계정 종류·홈 | 로그인 불가 시스템 계정, `/var/lib/somangapp` |
| 운영 모드·포트 | `NODE_ENV=production`, `PORT=3050` |
| PM2 작업 폴더·실행 파일 | `/var/www/somang-memorial/current`, `dist/index.js` |
| 앱 업로드 저장소 | `/var/www/somang-memorial/uploads` |
| 기존 PM2 관리 저장소 | `/root/.pm2` |

정비 전 읽기 확인에서 `current`는 `releases/20260907_160101`을 가리켰고,
배포된 Git SHA는 `c7811976cc203d824fcab80635488068e87b9604`였습니다.
계정 전환은 이 산출물을 유지한 채 진행할 수 있습니다. 새 빌드나 DB
변경이 필요한 작업이 아닙니다. 기쁨 홈페이지·기쁨 기념관·FaithPlus,
공용 Nginx, 다른 PM2 앱은 이 절차의 변경 대상이 아닙니다.

## 먼저 확보할 접근 권한

- `somangapp`의 실제 UID/GID를 확인하고 둘 다 0이 아닌지 확인합니다.
  숫자는 서버마다 다르므로 코드에 넣지 않습니다. sudo 권한은 주지 않습니다.
- 고정 상위 경로 `/var/www/somang-memorial`과 그 아래 `releases`는 관리자만
  바꿀 수 있어야 합니다. 기존에는 상위 경로에 다른 소유자가 있었으므로
  서버 담당자가 원래 소유자·그룹·모드를 기록한 뒤 **이 두 디렉터리 자체만**
  `root:root`, `0755`로 맞추는 1회 준비가 필요합니다. 재귀적으로 다른
  릴리스나 저장소의 소유권을 바꾸는 명령은 사용하지 않습니다.
- `current`의 실제 릴리스와 상위 폴더를 탐색할 수 있어야 합니다.
  `dist`, `node_modules`, `.env`는 읽을 수 있어야 하며 앱에 쓰기 권한을
  주지 않습니다. 기존 root 소유는 유지하고 전용 그룹의 읽기·탐색 권한만
  부여할 수 있습니다. `.env`는 예를 들어 `root:somangapp`, `0640`입니다.
- `UPLOAD_DIR`의 운영 설정을 먼저 확인합니다. 정비 전에는 별도 설정이
  없어 위 기본 경로를 썼고, 고정 래퍼도 같은 경로를 지정합니다. 경로를
  변경하는 경우에는 래퍼·백업·기존 사진 제공 경로를 함께 검토해야 합니다.
- 업로드는 `uploads`, `gallery/<기념관번호>`, `book-pages`, `book-covers`,
  `generated` 등의 하위 경로에 파일을 만듭니다. 기존 하위 폴더에도
  전용 그룹의 탐색·쓰기 권한을 주고, 새 하위 폴더가 그룹을 이어받도록
  setgid를 사용합니다. 기존 사진 내용·소유자를 바꾸지 않습니다.
- 앱은 백업 폴더와 root의 rclone 설정을 읽을 필요가 없습니다. 백업은
  기존 root 작업으로 유지합니다. 앱 실행 계정과 백업 실행 계정을 혼동하지 않습니다.

## 새 릴리스의 권한 준비 도구

`scripts/ops-runtime-permissions.py`를 검토한 뒤
`/usr/local/bin/somang-runtime-permissions.py`에 `root:root`, `0755`로
설치합니다. 앱이나 새 릴리스가 설치된 도구를 바꿀 수 있어서는 안 됩니다.
새 릴리스의 실제 경로를 `RELEASE_DIR`에 넣고, **빌드 완료 후 `current`
변경 직전**에 실행합니다.

```bash
/usr/bin/python3 -I /usr/local/bin/somang-runtime-permissions.py --release "$RELEASE_DIR" --check
/usr/bin/python3 -I /usr/local/bin/somang-runtime-permissions.py --release "$RELEASE_DIR" --apply
```

옵션이 없을 때도 점검만 합니다. 이 도구는 다음 범위만 다룹니다.

- `releases/YYYYMMDD_HHMMSS` 형식의 직접 하위 폴더만 받습니다. `current`
  별칭이나 다른 앱 경로는 받지 않으며, 아직 `current`가 가리키지 않는
  새 릴리스를 준비할 수 있습니다.
- 전체 릴리스와 고정 업로드 폴더를 검사하고, 변경 시작 직전에 다시
  검사합니다. 외부·끊긴 링크·특수 파일은 거부합니다. pnpm의
  `node_modules` 내부 링크만 확인 후 보존하며 링크를 따라 권한을 바꾸지 않습니다.
- `.git`은 위치와 관계없이 제외합니다. 릴리스 바로 아래의 `backups`,
  `archive`, `archives`, `releases`도 제외합니다. 앱 파일은 root 소유로
  두고 전용 그룹에 디렉터리 `0750`, 일반 파일 `0640`, 실행 파일 `0750`을
  줍니다. `.env`는 `root:somangapp 0640`, `.env.*`·`.env-*` 사본은
  `root:root 0600`으로 제한합니다.
- pnpm 파일은 다른 릴리스나 패키지 저장소와 같은 원본을 공유하는
  하드링크일 수 있습니다. 링크 수가 2개 이상이면 내용을 독립 파일로
  복사하고 SHA-256이 같은지 확인한 뒤 해당 릴리스의 이름만 원자적으로
  교체합니다. **다른 릴리스·패키지 저장소 원본의 권한은 바꾸지 않습니다.**
- 업로드는 디렉터리의 그룹과 setgid 권한만 조정합니다. 최상위는
  `root:somangapp 2775`, 하위 디렉터리는 기존 소유자와 `2775`를 유지·적용하며
  기존 사진 파일의 내용·소유자·모드는 변경하지 않습니다.

점검 결과에는 복사할 하드링크 개수·바이트 수가 나옵니다. 정비 당시에는
약 483MB의 공유 파일이 확인되었으므로 여유 공간도 확인합니다. 적용 중에는
같은 릴리스의 빌드·배포나 업로드 쓰기를 동시에 진행하지 않습니다.
검사 이후 파일이 바뀌거나 복사에 실패하면 `current`를 바꾸지 않고 멈춥니다.
적용 전체가 하나의 트랜잭션은 아니므로 일부 권한 준비가 끝난 새 릴리스가
남을 수 있지만, 같은 내용으로 다시 점검·적용할 수 있습니다.

강제 종료로 `.somang-permissions-*` 임시 사본이 남아 있으면 자동으로
권한을 넓히거나 삭제하지 않고 중단합니다. 관리자가 내용과 작업 기록을
확인한 뒤 처리합니다. 업로드가 실제로 읽히는지와 시험 파일 생성은
준비 상태 주소와 별도로 검증합니다.

## 고정 재시작 명령 설치

검토한 `scripts/ops-pm2-restart.sh`를 관리자만 바꿀 수 있는 위치에 설치합니다.
설치 전 경로와 소유권을 확인하며, 앱이 쓸 수 있는 파일을 root로 실행하지 않습니다.

```bash
install -o root -g root -m 0755 scripts/ops-pm2-restart.sh /usr/local/bin/somang-pm2-restart
/usr/local/bin/somang-pm2-restart somang-memorial
```

래퍼는 root 호출인지, `somangapp`의 UID/GID가 모두 0이 아닌지, 기본 그룹이
`somangapp`인지 검사합니다. 앱 이름과 포트·업로드 경로를 바꾸는 추가
인수는 받지 않습니다. 호출자의 Node 설정을 지우고 고정된 PM2 프로그램으로
`--uid`·`--gid`를 매번 지정합니다. root PM2는 그대로 두고 앱의 `HOME`만
`/var/lib/somangapp`으로 지정합니다.

이 명령은 **기존에 등록된 소망 앱의 재시작용**입니다. 새 PM2 앱을 만들거나
실행 파일·작업 폴더를 변경하지 않습니다. 첫 설치와 매 배포 때 위 표의
PM2 경로가 맞는지 확인합니다. 전체 `pm2 save`, `pm2 restart all`, 서버
재부팅은 실행하지 않습니다. 재부팅 복구용 저장 항목도 필요하면 별도
백업 후 소망 항목만 조정하고 다른 앱 항목이 그대로인지 비교합니다.

## 다음 배포와 실패 시 복구

기존 `/root/somang-deploy.sh`는 새 릴리스 준비·환경파일 복사·백업·빌드 후
`current`를 바꾸고 `pm2 restart somang-memorial`을 호출합니다. 서버 담당자는
원본을 보관한 뒤 **정상 배포와 복구 안내의 두 재시작 호출 모두** 위 고정
명령으로 바꿉니다. 저장소의 래퍼를 추가하는 것만으로 기존 서버 스크립트가
자동 변경되지는 않습니다.

이 기존 스크립트에는 `pnpm exec drizzle-kit`의 마이그레이션 단계도 있습니다.
계정만 전환할 때는 전체 배포 스크립트를 실행하지 않고 현재 산출물과 고정
재시작 명령을 사용합니다. DB 변경은 별도 검토가 필요한 단계입니다.

1. 새 릴리스의 빌드를 마친 뒤 위 권한 준비 도구를 설치된 절대 경로로
   호출합니다. 기존 환경파일 복사 단계는 `0600`을 사용하므로 래퍼만
   바꾸면 다음 배포가 실패합니다. 두 작업을 함께 연결해야 합니다.
2. `current` 변경 전에 전용 계정으로 실행 파일·환경파일·의존성을 읽을 수
   있는지 확인하고 타입 검사·테스트·빌드를 통과시킵니다. 계정 정비를 위해
   DB 스키마 변경 명령을 실행하지 않습니다.
3. `current` 변경 후 고정 래퍼로 소망만 재시작합니다. 아래 검증이 실패하면
   기록해 둔 직전 릴리스로 `current`를 복원하고 같은 래퍼로 재시작합니다.
   복구 릴리스에도 전용 계정의 읽기 권한이 필요합니다.
4. 실제 프로세스의 UID/GID와 실행 경로, 홈·포트, Linux capability가 0인지
   확인합니다. `/healthz`와 `/readyz`뿐 아니라 사진 읽기·시험 파일 생성,
   로그인 화면·공개 검색을 확인합니다. `/readyz`는 DB 연결만 확인합니다.
5. 다른 PM2 앱의 PID·재시작 횟수와 저장 설정이 바뀌지 않았는지 비교합니다.

PM2 CLI로 환경을 갱신한 뒤에는 중첩된 `pm2_env.env` 객체가 비어 보일 수
있으므로 이것만으로 환경설정이 사라졌다고 판단하지 않습니다. PM2의
최상위 앱 설정과 실제 프로세스의 `/proc/<PID>/environ`을 기준으로 기존
앱 설정 24개가 동일한지 확인합니다. 비밀값은 메모리 안에서만 비교하고
결과에는 개수와 일치 여부만 남깁니다. UID/GID·앱 홈 등 이번 정비에서
의도적으로 고정한 실행 항목은 별도로 검증합니다.

사진 쓰기 검증은 식별 가능한 시험 파일로 수행하고 기존 사진이나 회원
정보를 덮어쓰지 않습니다. 계정 권한을 잘못 줬다면 권한 설정부터 고치며,
원인 확인 없이 앱을 root로 되돌리는 명령을 반복하지 않습니다.

## 오래된 릴리스 보관

`scripts/ops-release-archive.py`는 원본을 삭제하는 대신 별도 보관함으로
옮깁니다. 기본 실행은 이름 목록과 선정 이유만 보여 줍니다. 서버 담당자가
검토 후 `/usr/local/bin/somang-release-archive.py`에 `root:root 0755`로
설치하고, 기존 배포의 정상 확인이 모두 끝난 마지막 단계에 연결합니다.
이 도구를 설치하기 위해 전체 배포나 DB 변경 단계를 다시 실행하지 않습니다.

```bash
/usr/bin/python3 -I /usr/local/bin/somang-release-archive.py
/usr/bin/python3 -I /usr/local/bin/somang-release-archive.py --apply
```

원본 위치는 `/var/www/somang-memorial/releases`로 고정하며,
`YYYYMMDD_HHMMSS` 형식의 실제 직계 디렉터리만 다룹니다. 다음 항목은
항상 남기므로 보관 후 원본 위치에 **5개보다 많이 남을 수 있습니다.**

- 이름 시각 기준 최신 5개 릴리스. 같은 코드의 사본도 이번 도구에서는
  각각 하나의 릴리스 폴더로 셉니다.
- `current`가 실제로 가리키는 릴리스.
- 모든 PM2 앱의 작업 폴더·실행 파일과 `/proc`의 프로세스 작업 폴더가
  참조하는 릴리스. 다른 앱이 소망의 옛 경로를 참조해도 보호합니다.
- `dump.pm2`, `dump.pm2.bak`에 저장된 실행·복구 경로가 참조하는 릴리스.

이동 위치는 `/root/somang-release-archive`이며 root만 접근할 수 있는
`0700` 권한을 사용합니다. 원본과 보관함이 같은 파일시스템인지 확인하고
`rename`만 사용합니다. **원본 파일의 내용·소유권·권한·inode를 유지하는
순수 보관 이동이므로 디스크 여유가 늘지 않습니다.** 복사·압축·삭제나
동일 이름 덮어쓰기를 수행하지 않습니다. 기존 보관 이름과 충돌하면 멈춥니다.

`current.tmp`가 있으면 동시 배포 가능성이 있어 중단합니다. 전체 대상
검증 후 각 이동 직전에 보호 목록·앱 PID·현재 릴리스·저장된 복구 설정을
다시 확인합니다. 전후 3050의 `/healthz`·`/readyz`와 현재 `dist`의 내용
해시도 확인합니다. 상태가 바뀌거나 검사가 실패하면 이번 실행에서 옮긴
폴더만 역순으로 원래 위치에 되돌립니다. 복구 위치가 새로 생겼다면
덮어쓰지 않고 수동 복구가 필요함을 알립니다.

보관함의 `manifest-*.jsonl`은 root 전용 `0600` 기록입니다. 선정 이유,
원래 경로, 이동 의도·결과, 실패 시 복구 결과를 남깁니다. 프로세스 강제 종료나
전원 장애로 기록이 완료되지 않았다면 관리자가 기록과 양쪽 폴더의 inode를
대조한 뒤 복구합니다. 업로드 저장소와 백업 폴더는 이동 대상이 아니며,
옛 릴리스 안의 환경파일 사본도 비공개 보관함에서 기존 권한을 유지합니다.

옛 릴리스를 archive에 남겨도 이전 브라우저의 JS/CSS가 자동 제공되지는
않습니다. 새 빌드를 배포할 때는 현재 정적 파일 보존도 별도로 검토해야
합니다. 이번 계정 전환은 기존 `dist`를 유지하여 이 문제를 만들지 않습니다.

## 자동 확인

`pnpm test`에 고정 앱 인수, root 호출, 계정 UID/GID·기본 그룹, 악의적인
환경변수, 작업 폴더 실패 검사가 포함됩니다. 실제 PM2를 실행하지 않는
검사입니다. CI는 `bash -n scripts/ops-pm2-restart.sh`와 Python 권한 도구
검사도 실행합니다. 권한 검사는 Linux root의 임시 시험 폴더에서만 수행하며
실제 앱 경로·계정·PM2에 접근하지 않습니다. 공유 파일의 원본 보존, 내부·외부
링크, 누락 파일, 중간 실패, 반복 적용, 비밀 임시 사본의 노출 방지를 확인합니다.
보관 도구도 Linux의 별도 시험 폴더에서 보호 대상 선정, 동일 inode 이동,
외부 링크·이름 충돌·다른 파일시스템 거부, 상태·건강 검사 실패 시 복구,
복구 위치의 덮어쓰기 방지를 검사합니다. 시험은 실제 PM2나 HTTP를 호출하지 않습니다.
